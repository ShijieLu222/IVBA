# 产品范围与核心业务

## 1. 产品目标

为独立艺术空间、活动主办方和本地观众提供一个低成本、可信任的场地与活动平台，降低以下三类摩擦：

1. 独立场地难以稳定获得合适的租用申请；
2. 小型主办方寻找、预订和管理场地的流程分散；
3. 普通用户难以发现和购买本地独立活动。

## 2. 用户与权限模型

“用户类型”不应做成互斥账户类型。一个人可以同时是观众、活动主办方和场地方成员。

| 主体 | 主要能力 |
| --- | --- |
| 普通用户 | 浏览活动、购票、退款申请、保存活动、管理个人资料 |
| 活动主办组织 | 搜索场地、提交租用申请、创建活动与场次、管理票种和订单 |
| 场地组织 | 发布场地、维护空间与可用时间、处理租用申请、查看结算 |
| 平台管理员 | 审核内容、处理纠纷、管理用户/组织/订单、查看运营数据 |

权限应归属于“组织成员关系”，而不是写死在用户记录上。例如，同一用户可以是某主办组织的 owner，同时是另一场地组织的 staff。

## 3. 两条不同的交易链

旧 README 把两种 booking 混在了一起。新版必须在产品和数据模型中明确分开：

### 场地租用（Venue hire）

活动主办方 → 查询空间与可用性 → 提交申请/询价 → 场地方确认 → 支付订金或全款 → 形成场地租用订单。

### 活动购票（Event ticketing）

普通用户 → 浏览已发布活动 → 选择场次与票种 → 短时锁定库存 → 付款 → 获得电子票/二维码 → 入场核销。

两条链可以关联，但不能共用一张含糊的 `bookings` 表。场地租用与门票订单具有不同状态、付款方、退款规则和库存逻辑。

## 4. 重启版 MVP

### 网站

- 面向公众的首页、地点/分类搜索、活动详情与场地详情；
- 注册、登录、账户与组织成员管理；
- 主办方创建活动、场次和票种；
- 主办方搜索场地并发送租用申请；
- 场地方创建场地/空间、上传图片、管理可用性和申请；
- 用户购票、查看订单和电子票；
- 管理员进行内容审核和基础运营管理。

### App（iOS / Android）

- 活动发现、搜索和筛选；
- 活动详情、购票和订单历史；
- 电子票与二维码；
- 收藏与必要的订单通知。

主办方、场地方和管理员的复杂操作首期放在响应式网站中。App 首期不复制完整后台。

## 5. 明确不进入首版

- 好友关系、动态流和“朋友正在参加”；
- AI 推荐或复杂个性化推荐；
- 场地取消后的自动重新分配；
- 商业用户订阅套餐；
- 原生 App 内的完整场地/活动后台；
- 复杂财务报表和会计系统集成；
- 自建聊天系统（首版使用结构化申请消息与邮件通知）。

## 6. 核心成功指标

- 已发布且资料完整的活跃场地数；
- 场地租用申请 → 确认的转化率与平均处理时间；
- 已发布活动数及有售票活动比例；
- 活动详情 → 完成购票的转化率；
- 退款率、取消率和支付失败率；
- 30 天内复购用户比例。

## 7. 开发前必须由业务方确认的问题

1. 平台在两种交易中谁是 Merchant of Record（法律上的销售主体）？
2. 平台是否代收款并向场地方/主办方分账，还是只收平台服务费？
3. 场地租用首版是“申请并人工确认”，还是允许实时即时预订？
4. 退款、取消、改期、no-show 和纠纷规则分别是什么？
5. 活动是否可能面向儿童；是否有年龄限制和监护人数据？
6. 场地与活动内容由谁审核，发布前还是发布后审核？
7. Artspace Lifespace 是否拥有现成品牌、域名、隐私政策和 Stripe 账户？
