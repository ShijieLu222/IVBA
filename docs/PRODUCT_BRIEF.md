# 产品背景与产品定义

## 1. 文档状态

本文基于旧大学项目 README 重新整理，是重启版的产品基线，不代表 Artspace Lifespace 已正式确认所有商业规则。标记为“待确认”的内容必须在进入支付和生产开发前由业务负责人确认。

## 2. 项目背景

Artspace Lifespace 是一家社区艺术慈善机构，为艺术家、创作者和本地社区提供具有特色的独立空间。旧项目希望通过一个价格更可负担的数字平台，帮助独立教师、艺术家、活动主办方和小型场地减少对高收费商业平台及分散人工流程的依赖。

项目最初由大学团队开发，完成了部分 React Native、Web 和 AWS/Helix 架构，但在形成完整可上线产品前搁置。重启版不继续旧代码，而是保留业务价值，重新定义产品范围、交易模型、技术架构和交付顺序。

## 3. 当前问题

### 对独立场地方

- 缺少稳定、低成本的曝光和获客渠道；
- 询价、日历、报价、确认和付款分散在邮件、表格与聊天工具；
- 容易发生信息遗漏、时段冲突和重复预订；
- 难以统一查看空间表现、未来活动和结算状态。

### 对活动主办方

- 很难按地点、容量、价格、设施和可用时间找到合适的独立场地；
- 场地申请、活动创建、售票和订单管理分属不同工具；
- 商业平台费用可能不适合小型、社区型活动；
- 缺乏从“找场地”到“办活动和售票”的连续工作流。

### 对普通用户

- 独立、本地、低成本活动的信息分散，发现成本高；
- 活动资料、购票、退款和电子票体验不一致；
- 缺少集中查看订单、票券和活动变更的入口。

### 对 Artspace Lifespace

- 无法在一个系统中审核和管理场地、活动、用户、订单与纠纷；
- 缺少可靠数据判断哪些活动、场地和地区表现良好；
- 难以验证平台是否真正帮助独立艺术生态获得更多参与和收入。

## 4. 产品愿景

建立一个可信、低摩擦的独立场地与本地活动平台，让主办方可以找到并申请合适空间，让场地方更容易管理租用，让公众更容易发现和参加社区活动。

一句话价值主张：

> 从寻找独立场地，到发布活动和售票，在同一个可信平台中完成。

## 5. 产品原则

1. **独立生态优先**：围绕小型场地、艺术家、教师和社区活动设计，而非复制大型票务平台。
2. **先建立信任**：价格、费用、取消、审核和交易状态必须清楚可追溯。
3. **两条交易链分开**：场地租用与活动购票共享平台，但拥有不同订单、状态和退款规则。
4. **组织而非单一角色**：用户可加入多个组织，并在不同组织中拥有不同权限。
5. **Web 与 App 各司其职**：专业后台优先 Web；普通用户高频发现、购票和票券优先 App。
6. **隐私默认保护**：只收集完成服务所必需的数据，并从设计阶段考虑 UK GDPR。
7. **人工可运营**：自动化失败时，管理员必须能在审计范围内安全介入。

## 6. 产品参与者

| 参与者 | 定义 | 核心目标 |
| --- | --- | --- |
| 访客 | 未登录的网站或 App 用户 | 搜索和了解公开场地/活动 |
| 普通用户 | 购买或持有活动票券的个人 | 发现活动、购票、查看票券和处理订单 |
| 活动主办组织 | 组织活动、租用场地和出售门票的组织/个人经营主体 | 找场地、办活动、售票和管理参与者 |
| 场地组织 | 拥有或运营一个或多个场地的组织 | 发布空间、处理申请、管理日历和结算 |
| 组织 Owner | 对某个组织承担最高管理权限的成员 | 管理成员、付款资料和关键设置 |
| 组织 Staff | 被授权处理场地、活动或订单的成员 | 完成日常运营工作 |
| 平台管理员 | Artspace Lifespace 授权的运营人员 | 审核、客服、退款、纠纷和平台治理 |
| 平台分析人员 | 只读或受限数据访问人员 | 查看聚合业务表现，不处理敏感操作 |

用户身份和业务角色不能做成互斥枚举。一个用户可以是观众，同时是主办组织 Owner，也可以是另一场地组织的 Staff。

## 7. 两条核心业务链

### 7.1 场地租用

```text
主办方搜索场地
→ 查看空间、设施、价格指引和可用性
→ 提交日期与活动需求
→ 场地方接受、拒绝或提供报价
→ 主办方接受报价并付款（待商业规则确认）
→ 形成已确认的场地租用
→ 双方收到变更、取消和履约通知
```

首版推荐采用 request/quote/accept，而不是即时预订。独立场地的价格、设施和活动适配通常需要人工确认；待平台累积稳定数据后，再为标准化空间提供即时预订。

### 7.2 活动购票

```text
用户搜索活动
→ 查看场次、地点、票种、价格和限制
→ 选择票种与数量
→ 系统短时锁定库存
→ 用户付款
→ Stripe webhook 确认付款
→ 系统签发唯一电子票/二维码
→ 入场时核销
```

场地租用和门票订单可以通过活动关联，但绝不能共用一张含糊的 `bookings` 表。

## 8. 平台范围

### Website

- 公开场地、活动、搜索与详情页面；
- 普通用户账号和订单页面；
- 活动主办方完整管理后台；
- 场地方完整管理后台；
- Artspace Lifespace 管理和审核后台。

### App（iOS/Android）

- 普通用户活动发现、搜索、收藏和购票；
- 订单、电子票、二维码和通知；
- 首版不复制完整场地/活动后台。

### Go API

- 为 Website、App 和后台提供统一业务规则；
- 负责认证后的授权、订单、库存、付款、审核、通知和审计；
- PostgreSQL/PostGIS 是业务事实来源。

## 9. MVP 产品范围

MVP 必须形成真实闭环，而不仅是页面展示：

1. 场地方创建场地和空间，管理员审核后公开；
2. 主办方找到场地并提交租用申请；
3. 场地方处理申请并确认或拒绝；
4. 主办方创建活动、场次和票种并提交审核；
5. 用户在 Web/App 浏览活动并完成测试/真实支付；
6. 系统签发电子票并支持二维码核销；
7. 用户和运营人员能够查看订单、取消和退款状态；
8. 平台能够查看基础运营数据和完整审计记录。

## 10. MVP 以外

- 好友关系、动态流和朋友活动；
- AI/复杂个性化推荐；
- 场地取消后的自动重新分配；
- 复杂选座图；
- 商业订阅套餐；
- App 内完整主办方/场地方后台；
- 自建实时聊天；
- 会计软件和外部日历的深度集成；
- 多国家、多币种和完整国际税务；
- 微服务和复杂数据仓库。

## 11. 商业模式假设（待确认）

可能的收入方式包括：

- 对门票订单收取平台服务费；
- 对场地租用交易收取佣金或固定服务费；
- 后期向高频商业主办方提供订阅功能。

在 Merchant of Record、Stripe Connect 模式、税务、退款、拒付和负余额责任确认前，不得把任何收费模式视为最终决定。

## 12. 成功指标

### 供给

- 已审核、资料完整的活跃场地数量；
- 可被搜索的场地空间比例；
- 每月新发布活动数量。

### 交易

- 场地详情 → 租用申请转化率；
- 租用申请 → 确认转化率；
- 场地方平均首次响应时间；
- 活动详情 → 购票完成转化率；
- 支付失败、退款和取消率。

### 用户价值

- 首次购票用户 30/90 天复购率；
- 用户找到本地活动所需时间；
- 订单/活动相关客服率；
- 活动核销率。

### 平台健康

- 重复预订和超卖事件数必须为零；
- 未解决付款 webhook 和失败任务数量；
- 审核处理时间；
- 数据导出/删除请求按时完成率。

## 13. 关键依赖与风险

- Artspace Lifespace 是否仍为产品所有者及其实际运营资源；
- 场地和主办方是否愿意完成 Stripe/KYC onboarding；
- 平台在交易中的法律责任与保险安排；
- 冷启动阶段是否有足够场地和活动供给；
- UK GDPR、未成年人、营销 consent 和数据保留；
- 第三方地图、支付、邮件和 App Store 政策变化；
- 退款、取消和纠纷流程是否有人员实际处理。

## 14. 业务方必须确认

1. 首发城市、目标用户和初始场地名单；
2. Merchant of Record 与平台收费方式；
3. 场地租用是否确认采用 request/quote/accept；
4. 订金、尾款、退款、取消、改期和 no-show 规则；
5. 活动审核、场地审核和组织验证标准；
6. 是否允许面向儿童的活动及年龄数据范围；
7. 客服、纠纷、退款和紧急事件由谁负责；
8. 品牌、域名、Stripe、App Store/Play Store 和隐私政策所有权。
